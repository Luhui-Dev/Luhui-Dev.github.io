Cuatro arquitecturas de agentes de las grandes tecnológicas

Tema: Ingeniería de agentes

Publicado: 24 de noviembre de 2026

Última actualización: 24 de noviembre de 2026

Un agente es un programa que usa un modelo y puede llamar a herramientas para completar una tarea.

Un agente de atención al cliente, por ejemplo, puede entender una solicitud de reembolso y consultar una API para verificar la compra. La orquestación define qué se hace primero, qué pasos pueden ejecutarse en paralelo, cuándo hace falta la aprobación de una persona y quién recibe cada resultado. En ese proceso pueden participar agentes, código de la aplicación y personas que aprueban decisiones.

El diagrama muestra un uso típico de cada uno de los cuatro marcos públicos de Microsoft, OpenAI, Google y Anthropic. Veamos cómo se tramitaría la misma solicitud de reembolso con cada uno.

  • Microsoft Agent Framework permite definir ramas explícitas. El programa verifica el pedido y solicita aprobación. Según la decisión, continúa la ejecución o envía el caso a revisión manual.
  • OpenAI Agents SDK ofrece dos formas de colaboración. El agente de atención al cliente puede ceder la conversación a un especialista o pedirle que compruebe si corresponde el reembolso y responder después por su cuenta.
  • Google ADK permite que el código ejecute varios pasos en paralelo. Una rama comprueba la fecha de compra y otra pide a un agente que determine si la reclamación encaja en una excepción de la política. El flujo reúne ambos resultados.
  • Claude Agent SDK permite que el modelo elija el siguiente paso a partir del resultado de cada herramienta. Puede consultar el pedido, descubrir un contacto previo y leer el ticket antiguo hasta reunir la información necesaria.

Tres preguntas ayudan a comparar estos enfoques: ¿Quién decide el siguiente paso, qué guarda el entorno de ejecución y qué trabajo se repite tras un fallo?



Microsoft Agent Framework: Una ruta explícita para la aprobación

Microsoft Agent Framework reúne la colaboración entre agentes de AutoGen y los fundamentos de integración de aplicaciones de Semantic Kernel.[1] En un flujo, un Executor puede ejecutar código o un agente. Procesa los mensajes que recibe y envía el resultado al siguiente nodo, de modo que se puede seguir el recorrido de un caso.

Tras comprobar el pedido, el ejecutor de verificación emite un mensaje de «caso verificado». El ejecutor de aprobación envía una solicitud externa mediante un RequestPort. Si la persona responde al día siguiente, el flujo puede cargar un punto de control y seguir la rama que corresponda. Con los puntos de control habilitados, se guardan el estado del flujo y los mensajes pendientes para la siguiente ronda.

Es posible probar ambas rutas con mensajes simulados. Una aprobación conduce a la ejecución. Un rechazo deriva el caso a revisión manual. Quien audite un reembolso puede consultar la decisión directamente, sin reconstruir el razonamiento del agente a partir del historial de chat.



OpenAI Agents SDK: Dos rutas para una misma solicitud

Supongamos que un cliente dice: «Quiero que me devuelvan el dinero de la suscripción que compré ayer».

La aplicación pasa el mensaje y el agente de atención al cliente al Runner del SDK. El Runner consulta el modelo, ejecuta las llamadas a herramientas o las transferencias que este solicita y continúa la ejecución. Quien desarrolla la aplicación configura las herramientas disponibles y los agentes a los que se puede transferir la solicitud.

Ruta uno: Transferir la solicitud al agente de reembolsos (Handoff)[2]

El cliente solicita un reembolso → el agente de atención identifica la intención → el Runner cambia al agente de reembolsos → el agente de reembolsos consulta el pedido y responde

El cambio sucede en la misma ejecución. El agente de reembolsos pasa a estar activo y usa sus propias instrucciones y herramientas. Si falta el número de pedido, puede pedírselo al cliente directamente.

Ruta dos: Usar el agente de reembolsos como herramienta para comprobar si procede

El cliente solicita un reembolso → el agente de atención llama al agente de reembolsos → el agente de reembolsos devuelve su evaluación → el agente de atención utiliza el resultado para responder

La llamada inicia una subtarea. Cuando el agente de reembolsos confirma que el pedido cumple los requisitos, el agente de atención puede comprobar el estado del reembolso o responder al cliente.

Una transferencia cambia el agente activo. Al usar un agente como herramienta, se delega una tarea y se devuelve el resultado al agente original.

Si las reglas del negocio exigen aprobar los reembolsos de importe elevado, la aplicación puede aplicar esa regla y usar RunState para guardar la ejecución en pausa mientras se autoriza la llamada a la herramienta.



Google ADK: Si basta una condición, evita otra reunión con el modelo

Google ADK empezó con jerarquías de agentes y flujos predefinidos para ejecutar pasos en secuencia, en paralelo o en bucle. ADK 2.0 añade grafos de flujo explícitos.[3] Quien desarrolla la aplicación puede combinar código y agentes en el mismo grafo, definir el orden de los nodos y las condiciones de cada transición, y transmitir resultados estructurados mediante eventos.

El plazo del reembolso y las excepciones de la política se pueden comprobar en paralelo. Una rama calcula con código cuánto tiempo ha pasado desde el pedido. La otra pide a un agente que lea la reclamación y encuentre la cláusula aplicable. Con ambos resultados, el flujo aplica la regla del importe para decidir si necesita aprobación. Los pasos siguientes reciben el resultado de la comprobación del plazo y la cláusula aplicable, sin tener que releer las dos conversaciones completas.



Claude Agent SDK: Examinar la evidencia antes de decidir

Claude Agent SDK procede de Claude Code. Integra la gestión del contexto, las llamadas a herramientas y los controles de permisos en un bucle de ejecución.[4]

Para investigar un reembolso disputado, el agente lee primero la reclamación y el pedido. Si descubre que atención al cliente prometió una compensación, consulta el ticket anterior. Si la política cambió después, busca la versión que estaba vigente cuando ocurrió el incidente.

En una investigación más amplia, el agente principal puede repartir tareas entre varios subagentes. Si se habilita la herramienta Workflow, Claude también puede generar un script de JavaScript para coordinar comprobaciones en paralelo, contrastar resultados y sintetizarlos. El plan puede adaptarse a la tarea y el entorno de ejecución programa los pasos definidos en el script.

Esa flexibilidad encaja en la investigación. En el momento de emitir un reembolso, las reglas del negocio deben seguir controlando los requisitos y la autorización del pago.



Reflexiones finales

Los cuatro marcos afrontan la misma disyuntiva. Cuanto más clara sea una regla, más sentido tiene expresarla en código. Cuanto más dependa la tarea de lo que se descubra durante la ejecución, más margen necesita el modelo para ajustar el plan.

  • Microsoft hace avanzar el flujo mediante mensajes.
  • OpenAI permite transferir una conversación o delegar una subtarea.
  • Google combina la planificación de grafos con los agentes.
  • Claude puede examinar una tarea y convertir el plan en un script.
