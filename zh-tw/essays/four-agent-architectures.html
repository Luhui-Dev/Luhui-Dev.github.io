四種大廠在用的 Agent 架構

主題: Agent 工程

發布日期: 2026年11月24日

最後修改: 2026年11月24日

Agent 是由模型驅動、能呼叫工具完成任務的程式。

比如，客服 Agent 可以理解客戶的退款訴求，再呼叫訂單查詢介面核對購買記錄。編排 是安排整個任務怎麼執行，包括先查什麼、哪些步驟能同時做、何時需要人工審核，以及每一步的結果交給誰。參與編排的可以是 Agent，也可以是業務程式碼和人工審核環節。

我整理了 Microsoft、OpenAI、Google 和 Anthropic 四套公開 Agent 框架的典型用法。讓我們用一筆退款申請來理解：

  • Microsoft Agent Framework 適合表達有明確分支的流程。程式查核訂單後發出審核請求，等人工回覆，再按結果繼續執行或轉人工處理。
  • OpenAI Agents SDK 支持兩種 Agent 協作方式。客服 Agent 可以讓退款專員接手本輪對話，也可以只讓專員核對退款資格，拿到結果後由客服 Agent 繼續回覆。
  • Google ADK 可以由程式碼安排多個步驟同時執行。例如，一邊核對購買時間，一邊讓 Agent 判斷投訴是否符合政策例外，兩邊完成後再彙整。
  • Claude Agent SDK 讓模型根據每次工具呼叫的結果決定下一步。例如，先查訂單，發現客戶曾聯繫過客服，再查舊工單，直到掌握足夠的資訊。

比較這四種編排方式時，可以問三個問題：誰來決定下一步，執行階段儲存了什麼，失敗後會重做什麼？



Microsoft Agent Framework：審核得走審核的路

微軟用於多 Agent 協作的 AutoGen 和面向應用集成的 Semantic Kernel 已經匯入了同一個框架。[1] 工作流里的 Executor 可以執行普通程式碼，也可以執行 Agent。執行器收到訊息才開始處理，然後把結果發給後續節點。業務流程可以沿著一條條訊息追蹤。

訂單查核完，驗證執行器發出「案件已查核」。審核執行器透過 RequestPort 發出外部請求。審核人第二天才回覆，工作流可以加載檢查點繼續，按核准或拒絕走不同分支。啟用檢查點後，執行階段會儲存工作流狀態和下一輪待投遞的訊息。

這套設計的好處是，審核流程可以直接用模擬訊息測試。給「核准」應走向執行，給「拒絕」應走向人工處理。審計人員追一筆退款時，能查到審核結果，省得從聊天記錄里考證 Agent 當時的心路歷程。



OpenAI Agents SDK：同一條退款請求的兩種執行路徑

以使用者發來一句「我想退掉昨天買的會員」為例。

應用把這條訊息和客服 Agent 交給 SDK 的 Runner。Runner 負責推進每一步，先呼叫客服 Agent 的模型，拿到輸出後執行它選中的工具或交接，再繼續執行。開發者事先配置客服 Agent 有哪些工具、可以把請求交給誰。

路徑一：把請求交給退款 Agent（Handoff）[2]

使用者發起退款請求 → 客服 Agent 識別退款意圖 → Runner 切換到退款 Agent → 退款 Agent 查詢訂單並給出回覆

切換發生在同一次執行中。退款 Agent 成為當前執行的 Agent，接下來用自己的指令和工具處理請求。如果訂單號缺失，它可以直接在回覆里請使用者補充。

路徑二：讓退款 Agent 只核對資格（Agent as a Tool）

使用者發起退款請求 → 客服 Agent 呼叫退款 Agent → 退款 Agent 返回資格核對結果 → 客服 Agent 根據結果回覆使用者

這次呼叫會啟動一個子任務。退款 Agent 返回「訂單符合退款條件」後，客服 Agent 拿到這個結果，可以繼續查退款進度，也可以直接回覆使用者。

兩條路徑的區別在 「接管」改變當前由誰處理請求，「呼叫／返回」把一項工作交出去，再把結果交回原來的 Agent。

如果業務規定大額退款須審核，應用可以把這條規則寫進業務流程，並用 RunState 儲存退款工具呼叫等待審核時的狀態。



Google ADK：能寫成條件判斷，就少開一次模型會議

Google ADK 從 Agent 層級和預設工作流 起步，支持順序、平行和循環。ADK 2.0 增加了 顯式工作流圖[3]，開發者可以把普通程式碼和 Agent 放在同一張圖里，定義哪個節點先跑、哪條邊能走。節點之間還可以透過事件傳遞結構化輸出。

退款時限和政策例外可以平行查。左邊用程式碼算訂單有多舊，右邊讓 Agent 讀投訴、找適用條款。兩邊各自返回結果，彙整節點收齊後，金額規則決定案件去審核還是繼續處理。這樣，後續節點拿到的是「是否超期」和「適用哪一條政策」，省去了把兩路的完整對話再讀一遍。



Claude Agent SDK：先看現場，再排下一步

Claude Agent SDK 來自 Claude Code。它把脈絡管理、工具呼叫和權限控制帶進一個持續執行的工具循環。[4]

比如調查一筆有爭議的退款時，Agent 先讀投訴和訂單。查到客服曾經承諾補償，就去找舊工單。發現涉及一條後來改過的政策，就去查事發時的版本。

材料多起來的話，主 Agent 可以叫多個子 Agent 分頭調查。啟用 Workflow 工具後，Claude 也可以先為當前任務生成一段 JavaScript 腳本，把平行核查、交叉驗證和彙整寫進去，再交給執行階段執行。計劃可以隨任務變化，腳本定下來的步驟則由程式調度。

這份自由適合調查類任務。實際執行退款時，資格校驗和付款審核仍應由業務規則控制。



寫在最後

幾家框架最終都在處理同一個矛盾：規則越明確，越值得交給程式碼。任務越依賴現場資訊，越值得給模型留出調整計劃的空間。

  • 微軟把流程推進做成訊息傳遞；
  • OpenAI 讓 Agent 在接管會話和委派子任務之間選擇；
  • Google 把圖調度與 Agent 放在一起；
  • Claude 可以讓模型先看任務，再把計劃寫成腳本。
